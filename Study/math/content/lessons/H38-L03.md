# 比较不同解法的效率

效率比较要先保证两种方法正确地解决同一个问题。本课以“寻找最小够用水箱容量”为例，用完整五天供水模拟的调用次数作为成本指标。调用次数不是实际秒数，也不是代码字数；输入范围、目标和判据都要保持一致。

## 固定候选与判据

使用名义雨水模型：A20m²、η3/4、雨量[6,0,0,6,0]mm、每日30L、初始0、先收后用。候选是0至150L的所有整数，共151个。判据P(C)表示这个容量能否满足每天需求。每次调用都计算完整五天，寻找第一个true；若一个也没有，报告无候选满足。

为什么可以二分？容量更大、期初存水不小时，min(C,s+I)不会减小；扣同一需求并截到非负后，日末存水也不会减小。由初始0逐日归纳，增加容量不会增加缺水。所以P(C)一旦从false变true，后续不再变回false。这是前提，不是二分程序自己创造的事实。

### 例1：同一问题的91次与7次

逐个扫描0,1,2,…，在90第一次合格。因为0也试，共91次，不是90次。二分使用半开范围：lo=0、hi=151，试mid=floor((lo+hi)/2)。若合格，令hi=mid保留左侧和mid；否则令lo=mid+1。lo=hi时结束，若等于151则没有有效候选。

具体试75失败，113成功，94成功，85失败，90成功，88失败，89失败，最后lo=hi=90，共7次。每个成功都继续寻找更小者，而不是第一次碰到113就停止。两方法得到相同的最小容量，才有资格比较调用次数。

### 例2：最坏情况与一个失效前提

151个候选逐个扫描最坏151次；这种二分最坏上界ceil(log2(152))=8。当前实际7次不等于最坏8次。若上限只有60，所有候选都失败；算法应报告没有候选满足，不能把范围外的61当成答案。

现在改判据为“每天够用，且费用40+2C≤240”。供水要求C≥90，预算要求C≤100，联合可行段90..100。C90真、C110假，已经不是向上封闭。盲把这个联合判据交给同一二分，可能完全跳过有效窗口。可以先求单调供水阈值，再检查费用；也可以完整枚举有限目录，保持正确性。

## 比较什么，结论就限定什么

工作台对同一输入分别运行扫描和二分，记录结果、实际次数、二分过程与最坏上界。含预算的窗口情形明确拒绝不适用的二分；更长干期则可能所有容量都不够，因为不足的是早期进水，不是计算方法。示意图的分半只说明策略，核验表保留每次lo、hi、mid与判据。

如果一种实现提前发现缺水就结束当天模拟，另一种总算完五天，两者单次调用成本已不同，需要另设指标或统一工作。即使调用更少，实际耗时仍受实现、输入和环境影响；这里只比较声明的模型计算次数，不宣称测得固定速度倍数。

出口要求解释两方法实际与最坏次数、供水单调性的理由和预算反例，由人审核。家长可问“每次计数包含同一工作吗”和“这个判据会不会变回失败”；若只背“二分更快”，先回到单调条件与有限候选，明确到底找什么。

# Comparing solution methods

Compare efficiency only after establishing that both methods solve the same problem correctly. Here the task is finding the smallest tank that supplies every day. Count calls to a full five-day simulation. Calls are not seconds or code length; hold the input range, objective and predicate fixed.

## Fix candidates and the predicate

Use the nominal model: A20 m², η3/4, rainfall [6,0,0,6,0] mm, demand 30 L/day, initial zero and collection before use. Candidates are all integer capacities from zero through 150, giving 151 values. P(C) states that every daily demand is met. Each call computes all five days; find the first true candidate or report none.

Binary search needs monotonicity. With greater capacity and no smaller opening storage, min(C,s+I) cannot decrease. Subtracting the same demand and truncating at zero preserves closing-storage order. Inducting from initial zero, greater capacity cannot increase deficit. Once P(C) becomes true, it stays true. This property justifies the search; the procedure itself does not establish it.

### Example 1: Ninety-one calls versus seven

Linear scanning tests 0,1,2,… and first passes at ninety. Zero counts, so this takes 91 calls. Binary search uses an exclusive upper bound: lo=0, hi=151 and mid=floor((lo+hi)/2). On success set hi=mid to keep that value and smaller candidates; on failure set lo=mid+1. Stop at equality. A result of 151 means no valid candidate.

The tests are 75 false, 113 true, 94 true, 85 false, 90 true, 88 false and 89 false. The final boundaries meet at ninety after seven calls. Success at 113 did not end the search because a smaller passing candidate might exist. Only after both methods return the correct same threshold is the call comparison meaningful.

### Example 2: Worst cases and a broken assumption

Linear worst case is 151 calls. For this binary procedure the worst-case bound is ceil(log2(152))=8. The realised seven-call run differs from that worst case. If candidates end at sixty, every candidate fails; return none rather than an out-of-range value sixty-one.

Now require both daily supply and cost 40+2C≤240. Supply needs C≥90, while budget needs C≤100, giving a middle window 90..100. C90 is true but C110 is false, so the joint predicate is not upward-closed. Blindly applying the same binary search can miss the entire window. Find the monotone supply threshold and then check cost, or enumerate the finite catalog with all constraints.

## Bound conclusions by the cost measure

The workbench records answers, actual calls, binary steps and its worst-case bound. It refuses unjustified binary search for the budget window. A longer dry spell may make every tank fail because inflow is insufficient, not because the search was inefficient. The audit retains lo, exclusive hi, mid and each result.

If one implementation stops a simulation at its first failure while another calculates all five days, their per-call work differs. Change the metric or standardise the work before comparing. Fewer calls do not establish a fixed measured speedup; runtime depends on implementation, inputs and environment. The exit explains actual and worst cases, monotonicity and the budget counterexample for human review. Ask whether every counted call contains the same work and whether the predicate can become false again. Return to the task definition and monotone condition before memorising that binary search is faster.
